# Экосистема сторонних клиентов Zvuk

**Срез на 2026-10-31.** Это обзор публичных README, changelog, справки сервиса и обсуждений. Код сторонних проектов не копировался. Совместимость и сетевые вызовы здесь не запускались; API-контракты ниже — заявления авторов проектов, а не официальная спецификация Zvuk.

## Короткий вывод

У Zvuk есть несколько работающих направлений сторонней интеграции: CLI-скачивальщики, библиотеки API на Python/Swift/Go/TypeScript, клиенты Murglar и Music Assistant, несколько нативных/обёрточных desktop-плееров, а также интеграции браузера и умной колонки. Официального публичного API для сторонних клиентов в изученных источниках не найдено. Практическая документация возникает из реверс-инжиниринга веб-приложения и регулярно расходится при изменениях сервиса.

В публичных материалах прослеживается смешанный API-контур: профиль/токен и некоторые потоковые операции Tiny API, GraphQL для каталога и пользовательских действий; проекты также сталкиваются с временными URL потоков и антибот-проверками. Токен аккаунта — секрет уровня учётных данных. `X-Auth-Token`, cookie `auth` и поле `token` описаны разными проектами, но это **не доказывает**, что один и тот же способ подходит ко всем endpoint’ам или что cookie всегда требуется отдельно.

## Telegram, браузер и парсинг веб-плеера

- В Telegram обнаружен [@zvuk_com_bot](https://t.me/zvuk_com_bot), но это официальный бот подкаста «Бит за бит», а не клиент для прослушивания/загрузки музыки. Также есть официальный канал [@zvuk_sound](https://t.me/s/zvuk_sound) и поддержка. В ходе поиска не подтвердился отдельный сторонний Telegram-бот, который выступал бы клиентом Zvuk или документировал его API. Это ограниченный результат поиска, не утверждение, что такого бота нигде нет.
- [SoundDLib](https://github.com/ivanvit100/SoundDLib) заявляет браузерную загрузку треков и плейлистов и кнопку, встроенную в сайт. Но репозиторий прямо помечает проект как находящийся в разработке; инструкция использования и технические детали отсутствуют. Поэтому README подтверждает намерение проекта, но не объясняет/не доказывает работающий способ извлечения потока.
- [SpotiShush](https://github.com/GUiHKX/spotishush) поддерживает Zvuk как расширение, которое временно выключает звук вкладки во время аудиорекламы. Оно не является API-клиентом и не описано как парсер потоков.
- Userscript [Open in Murglar](https://greasyfork.org/en/scripts/547150-open-in-murglar) добавляет кнопку для передачи страницы Zvuk в Murglar. Это deeplink-интеграция, не парсер плеера.
- [Web Scrobbler issue #6272](https://github.com/web-scrobbler/web-scrobbler/issues/6272) — свежий баг-репорт о коннекторе Zvuk в Firefox (25 октября 2026). Это свидетельство чтения состояния веб-плеера для скробблинга, а не загрузки аудио.

## Что сторонние источники раскрывают об API

### Слои и операции

Публичные клиенты показывают набор контрактов для анонимной/пользовательской авторизации, поиска, метаданных каталога, коллекций и лайков, редактирования плейлистов, рекомендаций/«Волн», текстов и выдачи URL потока. В Python-библиотеке это обёрнуто как 58 методов; автор указывает GraphQL и перечисляет запросы/мутации в changelog. Источники расходятся по тому, какие именно операции идут через GraphQL и Tiny API; это меняется со временем. Практический вывод — не зашивать один endpoint или форму ответа как стабильный внешний API.

Официальный инженерный материал Zvuk на Хабре описывает GraphQL Federation/микросервисную архитектуру для внутренних клиентских запросов: клиенты запрашивают только необходимые поля, GraphQL объединяет данные нескольких сервисов. Это подтверждает использование GraphQL внутри продукта, но **не публикует** контракт для сторонних приложений. Официальный материал: [«Как упростить жизнь за 312 коротких шагов: проектируем GraphQL API в микросервисной архитектуре»](https://habr.com/ru/companies/zvuk/articles/698352/).

Отдельно, changelog Swift/Python-клиентов называет получение прямого (non-DRM) URL через Tiny API. Некоторые интеграции сообщают, что адрес потока протухает и должен разрешаться заново перед воспроизведением. Не следует считать URL постоянной ссылкой или локальным файлом; ни формат ссылки, ни её срок жизни не опубликованы Zvuk как стабильный контракт.

Это чувствительный секрет; хранить локально защищённо, не логировать и не передавать в отчёты. |
| Cookie `auth` | README Rust CLI описывает cookie `auth` как источник личного токена; Go-клиент использует браузерный login и сохранение auth token. | По документации проектов cookie может быть контейнером той же сессии/токена, но нельзя заключить, что весь cookie jar обязателен для каждого запроса. Не копировать cookie в облачный сервис/бота. |
| `X-Auth-Token` | Node.js downloader и актуальный адаптер Music Assistant называют этот заголовок для авторизации. | Заголовок подтверждён в конкретных клиентах, но нет официальной спецификации, что он заменяет cookie для всех ручек. |
| `Origin`, `Referer`, `User-Agent` | Плеер для Яндекс Станции сообщает, что именно эти обычные заголовки нужны его запросам из-за антибот-защиты. В новых changelog Music Assistant есть сообщения о блокировке запросов профиля и потоковых ссылок. | Это контекстные требования конкретного сценария/текущей защиты, а не доказательство глобальной обязательности. Не проектировать продукт вокруг маскировки автоматизации или обхода защит. |
| Браузерная сессия / anti-bot cookie | ym2zvuk описывает ручной вход в настоящий браузер и использование запроса к `/api/tiny/profile` для priming anti-bot cookie. | Отдельно от пользовательской авторизации может существовать временная защита/состояние сессии. Проект прямо хранит захваченные данные локально; это хороший индикатор чувствительности, а не стандарт OAuth-flow. |

Смена пароля инвалидирует токен веб-сессии по документации плеера для станции. Рассматривать токен как пароль: защищённое хранилище macOS Keychain, минимальные логи, очистка при выходе/сбросе, отдельный безопасный экран ввода. Не помещать его в командную строку, URL, issue или crash-report.

### HiFi, обычное качество и URL потока

- Официальная [справка Zvuk о HiFi](https://help.zvuk.com/article/74576) называет формат FLAC без потерь, 16 бит, до 1411 кбит/с (CD quality); официальный FAQ говорит, что Hi-Res не поддерживается. Это потолок формата, не обещание такого битрейта для каждого трека и не показатель потока после Bluetooth/ОС.
- Официальные [Условия использования, п. 9.2](https://zvuk.com/terms) формулируют право Premium-подписки слушать **отдельный** контент в качестве 320 кбит/с и/или Hi-Fi; отдельная таблица со стабильными URL для тарифов не опубликована. Справка указывает, что часть веб-функций есть и без подписки, с ограничениями.
- Сторонние Python/Swift SDK и Murglar описывают уровни `mid` = MP3 128 кбит/с без подписки, `high` = MP3 320 кбит/с с подпиской, FLAC с подпиской. Это наиболее согласованная публичная матрица, но неполная и трек-зависимая. Официальные документы формулируют права через Premium и «отдельный контент», поэтому не следует превращать эту таблицу в гарантию на все позиции каталога.
- Третий клиент может запросить качество, но реальный URL/формат выбирается сервером с учётом прав пользователя и наличия версии у конкретного трека; свежий адаптер Music Assistant сообщает о fallback FLAC → MP3 320/128. Сторонние README/код не дают основания считать, что URL можно переиспользовать или что можно получать подписочное качество без активной подписки.
- В некоторых неофициальных README упоминаются FLAC 24 bit, но официальный FAQ подтверждает 16 bit / до 1411 кбит/с. 24-bit не следует считать официальной гарантией сервиса.

## Юридический статус и формулировки проектов

Юридический вывод о конкретном приложении зависит от способа использования, территории и прав на контент; это не юридическая консультация.

- Действующие [Условия Zvuk](https://zvuk.com/terms) дают пользователю личную непередаваемую лицензию на использование ПО в пределах его функциональности и для личных некоммерческих целей. Пункты 5.3 и 10.1 запрещают, в частности, копирование/воспроизведение контента и действия с сайтом/приложением вне предусмотренной функциональности без письменного разрешения. Пункт 9.2 разрешает Premium-пользователю подгружать контент для офлайн-прослушивания; это не тождественно лицензии на экспорт обычных музыкальных файлов в произвольный плеер.
- Авторы YAMP прямо говорят, что клиент не связан с Zvuk и не одобрен им, а права на контент принадлежат Zvuk. Авторы `zvuk-music` и `zvuk-swift` также указывают, что проект не связан и не одобрен сервисом; SDK требует авторизованный аккаунт/платную подписку для полного доступа.
- Не все проекты публикуют юридический дисклеймер. Упоминание MIT/Apache в репозитории относится к исходному коду приложения/библиотеки, а не к музыке и не предоставляет прав на API или контент. Ни наличие подписки, ни открытый код сами по себе не снимают ограничений условий сервиса или прав правообладателей.
- В изученных источниках не найдено официального разрешения Zvuk на неофициальные клиенты и не найдено судебного решения, объявляющего все такие клиенты законными/незаконными как класс. Дисклеймер проекта — позиция его автора, не заключение о правомерности.

## Практические выводы для desktop-клиента

1. Считать API неофициальным, изменяемым контрактом; отделить транспорт/GraphQL-запросы от моделей UI, снабдить интеграцию версией и диагностикой ошибок.
2. Использовать только токен самого пользователя и штатную подписку; хранить его в Keychain, не собирать пароль и не отправлять session cookie на свой сервер.
3. Разрешать URL потока по требованию при начале воспроизведения; не кэшировать его как постоянный адрес. Учитывать короткий срок жизни URL, fallback качества и ошибки подписки/антибота.
4. Опираться на официально доступные потоки, не обходить DRM/антибот-проверки и не экспортировать контент в обход предусмотренной функции офлайн-доступа.
5. Считать Electron `webview`-обёртки наиболее совместимыми и наименее зависимыми от реверс-инжиниринга, но ограниченными возможностями сайта; нативный клиент предоставляет лучший UX, но полностью зависит от нестабильных частных API.
